## The constraint changed the architecture, not just the tests

I expected "AI must auto-generate tests" to be a rule about the last phase of the project.
It turned out to be a rule about the second one.

My first sketch of the monitoring rules put them where they naturally belong in an
object-oriented design: as methods on the `Vehicle` model, reading thresholds from module
constants and calling `datetime.now()` when they needed the time. When I asked the AI to
generate tests for that design, what came back was technically valid and practically
useless — every test needed a database session, a committed vehicle row, and a patched
clock. Twenty lines of setup to assert that 118 °C is hotter than 115 °C.

So I inverted it. Each rule became a pure function over a frozen `EvalContext` carrying the
reading, the vehicle, the route, the previous reading, the thresholds, **and the current
time**. Nothing in `app/rules/` imports SQLAlchemy, FastAPI or the clock. A test became
three lines with no mocks. The 290-test suite now runs in under two seconds, which matters more
than it sounds: a suite that takes a minute gets run at the end, and a suite that takes a
second gets run constantly.

The lesson I did not anticipate: **a constraint on how you must test is a constraint on how
you must design.** Testability was not something I added to the architecture — it was the
thing that produced the architecture.

## Where AI genuinely accelerated the work

**Breadth on repetitive, well-specified work.** Once one rule existed as a pattern, the
remaining seven followed in minutes. The same held for the 37 functional requirements, the
Pydantic schemas, the CRUD routers and the ERD. This is work I know how to do; AI meant I
did not have to spend three evenings doing it by hand.

**Boundary cases I would have skipped.** Asked for "below, at, and above threshold, plus
`None` sensor fields", the AI produced parametrised tests that pinned down a decision I had
not consciously made — whether thresholds are inclusive or exclusive. Every threshold in
FleetPulse is exclusive: 105.0 °C is silent, 105.1 °C fires. I did not decide that, I
discovered it, and then the generated test froze it as intentional. Left to myself I would
have written `test_overheat_fires` and moved on.

**Documentation.** The API reference and the user manual were largely AI-drafted from the
running code. Rewriting the user manual for a non-technical reader was where I did most of
my own editing — the AI's first draft explained *what the buttons do*, and an operator needs
to be told *what to do when the screen turns red*.

## Where AI was wrong, and how I found out

This is the part I found most valuable, and it splits into three distinct failure modes.

### 1. Plausible code that was subtly broken

The AI wrote the harsh-braking rule as `drop / gap_seconds` with no guard on the gap. Real
telematics devices retransmit, so duplicate timestamps are routine — the rule would have
raised `ZeroDivisionError` in ordinary operation. Similarly, the haversine helper did not
normalise longitude differences, so a route crossing the antimeridian would have measured a
40,000 km deviation. Both were found by prompting the AI to attack its own code (P-19), and
both are now regression-tested. The generator did not find them; the *adversarial reviewer*
did, and it was the same model. The difference was entirely in what I asked it to do.

### 2. Tests that passed over a bug — the WebSocket case

This one changed how I think about generated tests.

The ingestion endpoint is a synchronous `def`, so FastAPI runs it in a worker thread. The
broadcast helper called `asyncio.get_running_loop()`, which raises in a worker thread; the
code caught the exception and returned silently. **Every live update triggered by telemetry
was being dropped.** The dashboard still looked alive, because the polling fallback quietly
covered for it.

The full suite passed. It passed *because* the AI had generated tests for the behaviour it
had written, including the broken part. I only found it when I sat down to write a test that
asserted a client actually receives an alert after ingestion — and had to reason about
threads to write it at all.

A generated test suite tells you the code matches its own assumptions. It cannot tell you
the assumptions were wrong.

### 3. A bug no unit test could have seen — the schedule rule

The schedule-delay rule projects arrival as `remaining_distance / speed`. Every unit test
passed: cruising speed projected sensibly, and zero speed fell back to accrued delay.
Neither I nor the AI wrote a test for **1.5 kph**, the speed of a bus easing into a stop.

At that speed the projection says the bus will arrive an hour late. When I ran twelve
simulated buses on real routes with real timetabled stops, the entire fleet lit up critical
at every stop. The unit tests were still green while the system was visibly, obviously
wrong on screen.

The fix was a speed floor below which the rule refuses to project. What I take from it is
that the failure was not in the code or in the tests — it was in the *space of cases anyone
thought to describe*. Only running the whole thing revealed the case in between the two I
had imagined.

## What I actually did by hand

Being specific matters here, because "AI-assisted" can mean anything.

- **Every architectural decision**, including the nine recorded with their rejected
  alternatives: pure rule core, cooldown-based deduplication, sweeper-based offline
  detection, SQLite over Postgres for portability, and dropping Leaflet for a self-drawn SVG
  map so the demo runs offline.
- **The deduplication semantics.** The AI's first alert service created one alert per
  firing. At a 5-second telemetry interval that is 720 alerts an hour from one hot engine.
  Cooldown windows, occurrence counting, and severity that ratchets up but never down are
  mine. So is measuring the cooldown from `last_seen_at` rather than `raised_at` — with the
  latter, a fault that never stops spawns a fresh alert every three minutes forever.
- **Snapshotting `measured_value` and `threshold_value` onto the alert row.** A deliberate
  denormalisation so that an alert stays interpretable after its source telemetry is pruned,
  and records the threshold *as it was when it fired* rather than as it is now.
- **All nine defect diagnoses and fixes.** The AI surfaced candidates; deciding which were
  real, what the correct behaviour should be, and where the fix belonged was mine.
- **Simulator tuning.** Ramp rates, stagger, and speed smoothing so that a demo shows values
  climbing through thresholds rather than a fleet that is either boringly healthy or
  uniformly broken. The first version snapped speed to zero at stops and tripped
  harsh-braking on every bus — a simulator artefact that looked exactly like a fleet-wide
  driver problem.

## Honest assessment of the result

FleetPulse does what it claims: 290 tests pass, the rule engine is at 98.8% coverage, and a
three-minute end-to-end run raises five distinct alert types from five armed faults while
deduplicating 402 readings down to 5 alerts.

What it does not do, and I would rather say so than let a marker discover it: there is no
authentication, the 200-readings-per-second throughput target was never load-tested, and the
accessibility work is implemented but not audited with a screen reader. Those are listed as
unverified in the test report rather than quietly claimed.

If I continued, the first three things would be authentication, a real load test against the
throughput target, and moving alert delivery beyond the dashboard to SMS or push — because
an alert nobody is looking at is not much of a monitoring system.

## What I would tell myself at the start

**Ask AI for the shape of the problem, then decide the semantics yourself.** It produced
eight competent rule implementations. Every decision that determined whether the system was
*usable* — deduplication, severity ratcheting, what an offline vehicle means, when a rule
should decline to judge rather than guess — was a judgement call that needed someone who had
imagined a person sitting in front of the screen at 2 a.m.

**Make it run before you believe your tests.** Four of the nine defects were invisible to a
fully green suite. The green tick is evidence, not proof.

**And beware the fix that passes its own regression test.** The schedule rule took three
attempts. D-07 diagnosed a bus crawling at 1.5 kph, added a test at 1.5 kph, went green, and
was recorded as closed — but the real problem was that instantaneous speed is the wrong
estimator at *any* value, and the defect simply reappeared at 6 kph as D-09. I had written the
test to my diagnosis rather than to the mechanism, so it pinned one arbitrary point on a
continuum and proved nothing about the point next to it. What finally settled it was not
another test but arithmetic: reconciling the stored `measured_value` of 695 s against the route
geometry identified the speed that produced it, and that pointed at the estimator instead of
the threshold. The fix is now backed by an 18-minute endurance run rather than by my
confidence.

**Prompt for the adversary, not just the author.** The single highest-value prompt in the
whole log was P-19: *"review this adversarially for defects the happy-path tests would
miss."* Same model, same code, opposite instruction — and it found four real bugs. The value
was not in the tool. It was in remembering to ask.
