## What it does

Buses and delivery trucks report position, speed, engine temperature, fuel and cargo
temperature every few seconds. FleetPulse evaluates each reading against eight operational
rules and raises a deduplicated, severity-ranked alert within seconds — so a problem is
caught while it is still preventable rather than after it has already cost something.

| Rule | Applies to | Fires when |
|---|---|---|
| `OVERSPEED` | both | Faster than the route limit plus tolerance |
| `ENGINE_OVERHEAT` | both | Engine temperature above warning / critical |
| `LOW_FUEL` | both | Fuel below low / critical |
| `ROUTE_DEVIATION` | both | Outside the route corridor (geofence) |
| `VEHICLE_OFFLINE` | both | Silent longer than the heartbeat timeout |
| `HARSH_BRAKING` | both | Large speed drop between consecutive readings |
| `SCHEDULE_DELAY` | **bus** | Projected late at its next timetabled stop |
| `CARGO_TEMP_EXCURSION` | **truck** | Refrigerated load outside its permitted band |

## Quick start — Docker (nothing to install but Docker)

```bash
docker compose --profile sim up --build     # → http://localhost:8000
```

One command builds the image, serves the API and dashboard on the same origin, seeds twelve
vehicles and starts a simulated fleet with five faults armed. Alerts begin appearing after
about 50 seconds. Details and a verified run: [`docs/12-docker-guide.md`](docs/12-docker-guide.md).

```bash
docker compose run --rm tests               # 290 tests, inside the image
docker compose down -v                      # stop and wipe the database
```

## Quick start — local development

```bash
# 1. Install
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
cd frontend && npm install && cd ..

# 2. Seed the demo fleet — 3 routes, 8 buses, 4 refrigerated trucks
cd backend && python -m app.seed --reset

# 3. Run (three terminals)
uvicorn app.main:app --reload          # API      → http://127.0.0.1:8000
cd frontend && npm run dev             # dashboard → http://localhost:5173
cd backend  && python -m app.simulate  # telemetry starts flowing
```

Make something go wrong on demand:

```bash
python -m app.simulate \
  --scenario BUS-03=overheat --scenario TRK-01=cargo_spike \
  --scenario BUS-05=deviation --scenario BUS-07=dropout \
  --scenario BUS-02=fuel_drain
```

Faults ramp rather than jump, so you watch the value climb through its threshold and the
alert appear live. Full options in [`docs/07-installation-guide.md`](docs/07-installation-guide.md).

**No internet and no database server are required either way.** SQLite is a file and the
dashboard draws its own map, so the whole project runs on a disconnected laptop.

## Architecture in one paragraph

A **pure core with I/O at the edges**. Every rule is a side-effect-free function over a
frozen context with the clock and all thresholds injected; nothing in `app/rules/` imports
SQLAlchemy, FastAPI or `datetime.now()`. Around that core sit thin layers that persist,
deduplicate, broadcast and serve. This shape is not decoration — it is what made the
mandatory AI-generated tests possible without a single mock, and it is why 290 tests run in
under two seconds.

```
Simulator / GTFS-RT ──▶ FastAPI ──▶ Ingestion ──▶ Rule engine (pure)
                                        │              │
                                        ▼              ▼
                                   SQLite/ORM ◀── Alert service (dedupe, lifecycle)
                                        │              │
                                        └──────▶ WebSocket hub ──▶ React SPA
```

Diagrams, decision records and rejected alternatives: [`docs/03-architecture.md`](docs/03-architecture.md).

## Tests

```bash
cd backend && pytest
# 290 passed in 1.2s — coverage: rules 98.8%, application 87%
```

Every test was AI-generated (prompts P-17, P-18, P-19). The adversarial pass and the demo runs found **nine
real defects**, including three that no passing test would ever have revealed — a WebSocket
broadcast that was being silently dropped, and an ETA projection that made the entire bus
fleet raise false alerts at every stop. Both are documented honestly in the test report.

## Known limitations

Stated plainly rather than left for a marker to find:

- **No authentication.** Explicitly out of scope; a single trusted operator is assumed.
- **Throughput target (200 readings/s) is unverified** — no load test was run.
- **Accessibility is implemented but not audited** with assistive technology.
- **No predictive/ML failure forecasting.** The engine is deterministic and rule-based by
  design, so that every alert can be explained to an operator.
- The GTFS-Realtime path requires vehicles to be pre-registered with matching codes.
