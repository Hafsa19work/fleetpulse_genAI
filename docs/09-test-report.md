## 2. How the Constraint Was Satisfied

Every test module in `backend/tests/` was produced from an explicit AI prompt, recorded
verbatim in `PROMPT_LOG.md`. Each file carries a header naming the prompt that generated it
and any manual correction applied afterwards, so a marker can trace a test back to the
instruction that produced it.

The constraint changed the **production** code, not only the test code. To make the rules
AI-generatable without mocks, they were written as pure functions over a frozen
`EvalContext` with the clock and every threshold injected. A test is then a literal:

```python
ctx = make_ctx(reading=make_reading(engine_temp_c=118.0))
(candidate,) = engine_temp.evaluate(ctx)
assert candidate.severity is Severity.CRITICAL
```

No database, no mock, no patching, no time-freezing library. That is why 290 tests run in
under two seconds — and it is a direct architectural consequence of a constraint on testing.

### What the generated tests actually assert

The prompts asked specifically for boundary and negative cases, not happy paths, and the
suite reflects that:

- **Three-point boundary testing on every threshold rule** — below, exactly at, and just
  above. Every threshold in FleetPulse is *exclusive*: 105.0 °C is silent, 105.1 °C fires.
  That decision is pinned by tests rather than left to a reader of the source.
- **Missing sensor data** — a `None` engine temperature, fuel level or cargo temperature
  must produce no alert and no exception. A truck without a temperature probe is not a
  faulty truck.
- **Vehicle-type gating** — `SCHEDULE_DELAY` is asserted absent for a truck with numbers
  that would trip it on a bus, and `CARGO_TEMP_EXCURSION` absent for a bus.
- **Deduplication and lifecycle** — two firings inside the cooldown produce one alert with
  `occurrences == 2`; severity escalates and never de-escalates; a resolved alert is
  terminal and a refire creates a new one; illegal transitions return 409.
- **Determinism of the simulator** — the same seed produces byte-identical output, which is
  what makes assertions about simulator behaviour meaningful at all.
- **Optional-dependency degradation** — the GTFS reader is tested through stub objects, so
  the suite passes whether or not `gtfs-realtime-bindings` is installed.

## 5. AI-Assisted Bug Detection — Defect Log

Prompt **P-19** asked the AI to attack its own implementation adversarially, looking for
defects the happy-path tests would miss. Seven real defects were found there; two more (**D-08**, **D-09**) surfaced later, from watching the
containerised demo run for long enough. Each got a failing
regression test *before* the fix, and every regression test is still in the suite.

| ID | Defect | How it would have failed in production | Fix | Regression test |
|---|---|---|---|---|
| **D-01** | Timezone-naive datetimes returned from SQLite compared against tz-aware `datetime.now(UTC)` | `TypeError: can't subtract offset-naive and offset-aware datetimes` on the first alert dedup lookup after a restart — i.e. the system would work in tests and crash in use | `ensure_utc()` applied to every datetime leaving the persistence layer | `test_api_alerts.py` timestamp assertions, `test_offline_sweeper.py` |
| **D-02** | Harsh-braking rule divided by the time gap without checking it | `ZeroDivisionError` whenever two readings shared a timestamp — and duplicate timestamps are exactly what a retrying field device produces | Gap must be strictly positive and within the window, else the rule declines to judge | `test_rules_harsh_braking.py::test_zero_time_gap_does_not_divide_by_zero`, `::test_negative_time_gap_is_declined` |
| **D-03** | Longitude differences not normalised | A route crossing the antimeridian would compute a ~40,000 km deviation and alert permanently | `normalize_lon_delta()` applied in every geodesic function | `test_geo.py::test_antimeridian_distance_is_short_not_a_lap_of_the_planet` |
| **D-04** | One raising rule aborted evaluation of the rest | A bug in the truck cargo rule would silently suppress an engine-overheating alert on a bus — a monitoring system failing exactly when it matters | Per-rule `try/except`; failures recorded in `failed_rules`, remaining rules still run (NFR-09) | `test_rules_engine.py::test_a_raising_rule_does_not_suppress_the_others` |
| **D-05** | A dead WebSocket client raised during broadcast | Closing a browser tab mid-broadcast would turn the *next telemetry ingestion request* into a 500 | Failed sends prune the client and are logged, never propagated | `test_ws_live.py::test_a_dead_client_is_pruned_not_propagated` |
| **D-06** | `broadcast_soon()` used `asyncio.get_running_loop()`, which raises inside a worker thread | Every WebSocket broadcast triggered by telemetry ingestion was **silently dropped** — the dashboard would have looked live but only ever updated by the 5-second polling fallback. Found while writing the WebSocket test, not by a failing assertion | The hub binds the application loop at startup and uses `run_coroutine_threadsafe` from worker threads | `test_ws_live.py::test_broadcast_soon_from_a_worker_thread_reaches_the_bound_loop`, plus the three live-push tests |
| **D-07** | Schedule ETA projection `remaining / speed` unstable at low speed | A bus dwelling at a stop at 1.5 kph projected an arrival over an hour away; **the entire bus fleet fired critical `SCHEDULE_DELAY` at every stop**. Found during the end-to-end demo run, not by the unit tests — the unit tests had only exercised 0 kph and cruising speed, never the crawl in between | `schedule_min_speed_kph` floor raised to 5 kph; below it the rule uses the delay already accrued | `test_rules_schedule.py::test_a_bus_crawling_at_a_stop_does_not_project_a_false_delay`, `::test_above_the_speed_floor_the_projection_is_used_again` |

### D-08 — found by looking at the screen, ten minutes in

| | |
|---|---|
| **Defect** | After ~10 minutes of continuous simulation, `SCHEDULE_DELAY` spread across the whole bus fleet with reported delays of 14–18 minutes. |
| **Why it happened** | Not a rule bug, and not a recurrence of D-07. A **modelling mismatch in the simulator**: buses *shuttled* back along their route at the terminus, but a timetable is defined in one direction only. Travelling backwards, the "next stop ahead on the polyline" is a stop the bus already served — with a small scheduled offset — while `trip_started_at` never moved, so elapsed time grew without bound. Every bus eventually reported itself late against a timetable it had already finished. |
| **Why nothing caught it** | The unit tests run 80 ticks; the drift needs ~120. The three-minute end-to-end run in §6 was also too short. It was found by leaving the container running and *looking at the dashboard*. |
| **Fix** | Buses now re-run the route from the start ("next service from the terminus") instead of reversing, and the simulator raises a `trip_restarted` flag that the CLI turns into `PATCH /api/vehicles/{code}` with a fresh `trip_started_at`. The `direction` field and its reversal logic were deleted; odometer and stop-dwell handling were corrected for the wrap. |
| **Regression tests** | `test_simulator.py::test_bus_restarts_the_route_at_the_terminus`, `::test_bus_reaching_the_terminus_reports_a_new_trip`, `::test_trip_restarts_are_drained_not_repeated` — plus a 14-minute continuous-run check confirming no `SCHEDULE_DELAY` appears. 279 → 282 tests. |

The honest framing: this is a **simulator** defect, not a production one. A real bus fleet
would send a genuine trip start. But it mattered, because a demo that shows twelve false
critical alerts teaches the examiner to distrust every alert on the screen — and the same
class of mistake (a test harness modelling the world differently from the system under test)
produces false confidence in the other direction just as easily.

### D-09 — the fix that wasn't: instantaneous speed is the wrong estimator

| | |
|---|---|
| **Defect** | After the D-08 fix, a 14-minute continuous watch **still** caught `SCHEDULE_DELAY` firing falsely — BUS-01 "11.6 min late", BUS-05 "7.7 min late". |
| **Diagnosis** | The recorded `measured_value` of 695 s reconciled exactly with a 2 km leg projected from a momentary **6 kph** — the speed a bus reads while accelerating away from a stop. D-07 had raised the floor on *instantaneous* speed from 1 kph to 5 kph, which only moved the failure a few kph up the scale. |
| **Real cause** | `remaining / instantaneous_speed` is a bad estimator in principle. A bus spends much of its time stopped or accelerating, so its speed at any instant says almost nothing about how long the rest of the leg will take. |
| **Fix** | Project from the **average speed since the trip began** (`along_vehicle / elapsed`), which already has dwell time, traffic and acceleration baked into it. `schedule_min_speed_kph` now floors that average; below it the rule still falls back to accrued delay. |
| **Regression tests** | `test_a_bus_dwelling_at_a_stop_does_not_project_a_false_delay` asserts silence at 0, 1.5, 6, 12 and 40 kph instantaneous for an on-schedule bus; `test_the_speedometer_reading_cannot_change_the_verdict` asserts two otherwise-identical readings agree. The whole schedule suite was rewritten to control position and elapsed time rather than the speedometer. |
| **Verified** | An **18-minute uninterrupted container run** — the check that failed for D-08 and D-09 — completed clean. See §6c. |

**This is the most instructive entry in the log, because the first fix passed its own
regression test.** D-07 added a test at 1.5 kph, it went green, and the defect was recorded
as closed. The test was written to the diagnosis rather than to the mechanism, so it locked
in one arbitrary point on a continuum and proved nothing about 6 kph. Only a long
uninterrupted run of the real system exposed it — and only arithmetic on the stored
`measured_value` identified the true cause rather than a third guess at the threshold.

### What the defect log says about AI-generated testing

D-06 and D-07 are the two most instructive entries, and both are arguments **against**
trusting a generated suite on its own:

- **D-06 was found by writing a test, not by running one.** The generated tests all passed
  before the fix, because they never asserted that a broadcast reached a client from the
  synchronous ingestion path. The AI generated tests for the behaviour it had implemented,
  including the broken part.
- **D-07 was invisible to the entire unit suite.** Every schedule test passed. The bug only
  appeared when twelve simulated buses drove real routes and pulled into real stops. A
  green suite proved the rule matched its own assumptions, not that the assumptions were
  right.

Both were caught because the project also runs end to end (§6). That is the finding
recorded in the reflection essay: AI-generated tests are excellent at breadth around code
that exists, and blind to the case nobody thought to describe.

## 6. End-to-End Verification

Coverage numbers do not prove the system works. This run does — a real API process, a real
SQLite file, the real HTTP ingestion path, and the background sweeper.

```bash
python -m app.seed --reset
uvicorn app.main:app --port 8010
python -m app.simulate --api http://127.0.0.1:8010 --ticks 36 --interval 5 \
  --scenario BUS-03=overheat  --scenario TRK-01=cargo_spike \
  --scenario BUS-05=deviation --scenario BUS-07=dropout \
  --scenario BUS-02=fuel_drain
```

**Observed after 3 minutes — 402 readings ingested across 12 vehicles:**

|---|---|---|---|---|---|
| critical | open | BUS-07 | `VEHICLE_OFFLINE` | 5 | BUS-07 has not reported for 3.5 min (timeout 2.0 min) |
| critical | open | BUS-03 | `ENGINE_OVERHEAT` | 23 | BUS-03 engine temperature 141.7 °C exceeds 115 °C |
| critical | open | TRK-01 | `CARGO_TEMP_EXCURSION` | 27 | TRK-01 cargo at −9.6 °C — 5.4 °C above the permitted limit of −15 °C |
| critical | open | BUS-05 | `ROUTE_DEVIATION` | 27 | BUS-05 is 432 m from route R-22B (corridor 120 m) |
| warning | open | BUS-02 | `LOW_FUEL` | 20 | BUS-02 fuel level 13% is below 20% |

Snapshot: `{total: 12, reporting: 11, ok: 7, warning: 1, critical: 3, offline: 1}`
Health: `{status: ok, readings_ingested: 402, alerts_raised: 5, database: ok}`

**Every behaviour this was meant to prove, proved:**

1. Five distinct rules fired, from five independently armed faults.
2. **Deduplication held.** 402 readings produced **5 alerts**, not 402. One persistent fault
   is one alert with a rising counter.
3. **Severity escalated.** BUS-03 first appeared as a `warning` at 105.7 °C and became
   `critical` as it passed 115 °C — the same alert row, ratcheted upward.
4. **Messages track live values.** BUS-03's message read 141.7 °C at the end of the run, not
   the 105.7 °C from when it first fired.
5. **The sweeper works.** BUS-07 stopped transmitting; nothing arrived to trigger evaluation,
   and the background sweeper raised `VEHICLE_OFFLINE` on its own (design decision D-7).
6. **Bus/truck gating held.** `CARGO_TEMP_EXCURSION` appeared only for a truck, and no bus
   raised a spurious schedule delay after the D-07 fix.
7. The four unarmed vehicles stayed silent for the whole run — the system does not cry wolf.
