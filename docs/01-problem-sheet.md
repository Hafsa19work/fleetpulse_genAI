## 2. Problem Statement

Public transport authorities and last-mile logistics operators run mixed fleets — city buses on
fixed timetabled routes and delivery trucks on dynamic multi-stop legs. Both bleed money and trust
for the same reason: **problems are discovered after they have already hurt someone.** A bus is
reported late only once passengers complain; an engine is found to be overheating only when it fails
on the road; a refrigerated load is found spoiled only at the delivery door; a driver's overspeeding
surfaces only in a monthly report.

The raw signals that predict all of these — position, speed, engine temperature, fuel level, cargo
temperature, heartbeat liveness — are already emitted by modern telematics units. What is missing for
small and mid-size operators is an affordable system that **continuously evaluates those signals
against operational rules and raises an actionable alert within seconds.**

**FleetPulse** is that system: a real-time monitoring service that ingests vehicle telemetry,
evaluates it against a configurable rule engine, raises deduplicated and severity-ranked alerts, and
presents the live state of the whole fleet on an operations dashboard.

## 4. Scope

### In scope
- Telemetry ingestion over REST (single reading and batch), for both **buses** and **delivery trucks**.
- Vehicle registry and route/geofence definition with waypoints and stops.
- A **monitoring rule engine** with eight rules: overspeed, engine overheating, low fuel,
  route deviation (geofence), vehicle offline (heartbeat timeout), harsh braking,
  schedule delay *(buses only)* and cargo temperature excursion *(trucks only)*.
- Alert lifecycle: raise → deduplicate within a cooldown window → acknowledge → resolve.
- Live **React SPA** dashboard: fleet map, KPI tiles, alert feed, per-vehicle telemetry history charts,
  and a threshold-tuning panel.
- A deterministic, seedable **telemetry simulator** with injectable fault scenarios, so the system can
  be demonstrated with no physical hardware.
- An **optional GTFS-Realtime reader** for ingesting a real public transit vehicle-position feed.
- An **AI-generated pytest suite** with a coverage report.

### Out of scope
- Driver identity management, payroll, ticketing or fare collection.
- Predictive/ML failure forecasting (the engine is deterministic and rule-based by design).
- Native mobile applications and SMS/push notification delivery.
- Multi-tenancy, authentication and authorisation (single trusted operator assumed; called out as
  future work in the reflection essay).

## 5. The Mandatory AI Constraint and How It Is Satisfied

Because the declared favourite technology is **Python**, Part A §3 imposes:
**“AI must auto-generate tests.”**

| Obligation | How FleetPulse satisfies it | Evidence |
|---|---|---|
| Tests are AI-generated, not hand-written | Every test module in `backend/tests/` was produced from an explicit AI prompt; the prompts are recorded as **P-17**, **P-18** and **P-19**. | `PROMPT_LOG.md` |
| Generation is reproducible and auditable | Each test file carries a header comment naming the prompt id that generated it and any manual correction applied afterwards. | `backend/tests/*.py` headers |
| Tests are meaningful, not cosmetic | Suite covers boundary values, `None` sensor fields, vehicle-type gating, alert deduplication and invalid state transitions; statement coverage is reported. | `docs/09-test-report.md` |
| AI also assists bug detection | An adversarial AI review pass (**P-19**) produced a defect log; each defect got a failing regression test before the fix. | `docs/09-test-report.md` §5 |

Note the deliberate design consequence, discussed in the reflection essay: because the tests had to be
AI-generatable, the rule engine was written as **pure, side-effect-free functions with injected
thresholds**. A constraint on testing therefore shaped the production architecture.

   a purely static dataset or a hard dependency on a live feed.
